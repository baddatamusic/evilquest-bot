EvilQuest Anti-Cheat Improvement Analysis
==========================================
Subject: How EvilQuest could detect or break the current bot
Perspective: Defensive — written from the game developer's point of view
Scope: All detection vectors observable from the server side


==========================================================================
1. TRANSPORT / TLS FINGERPRINTING
==========================================================================

1.1  JA3 / JA4 TLS Client Hello fingerprint
     The bot uses Python's ssl module via the websockets library. The TLS
     Client Hello it sends has a different cipher suite order, extension
     list, and elliptic curve preferences than a real Chrome browser. JA3
     hashes these fields into a single fingerprint. The bot's JA3 will
     never match Chrome's. The server could:
       - Log JA3 fingerprints for all connections.
       - Block or flag any fingerprint that does not match a known browser.
       - Libraries like Cloudflare's Bot Management do this by default.

1.2  HTTP/2 vs HTTP/1.1
     Chrome uses HTTP/2 with multiplexing, HPACK header compression, and a
     specific SETTINGS frame. Python's requests library defaults to HTTP/1.1.
     Even if the bot sends Chrome-like headers, the underlying protocol
     version reveals a non-browser client. The server could reject any login
     that arrives over HTTP/1.1 from a client claiming to be Chrome.

1.3  Header order and pseudo-header order
     Browsers send HTTP headers in a fixed, well-known order. Python's
     requests library sends them in a different order (e.g., User-Agent
     before Accept, or missing Accept-Language in the right position).
     HTTP/2 pseudo-headers (:method, :path, :authority, :scheme) also have
     a browser-specific order. Fingerprinting header order is difficult to
     spoof without a real browser engine.

1.4  Sec-CH-UA client hints
     Chrome sends Sec-CH-UA, Sec-CH-UA-Mobile, and Sec-CH-UA-Platform
     headers. These are generated by the browser from the real UA string and
     cannot be trivially faked because the server can request high-entropy
     hints that require JavaScript execution to generate correctly.


==========================================================================
2. HTTP LOGIN AND SESSION FINGERPRINTING
==========================================================================

2.1  No browser load sequence
     A real player opens the page, loads index.html, then CSS, fonts,
     images, the JS bundle, and finally makes the API calls. The bot skips
     straight to POST /api/login with no prior page load. The server could
     require that a valid session cookie from loading the front page exists
     before the login API accepts a request.

2.2  Missing or wrong Referer / Origin timing
     The bot sends Origin and Referer headers to mimic a browser, but the
     timing between page load and login POST is instant. Real users take
     seconds to type credentials. The server could reject logins that arrive
     less than ~2 seconds after the session cookie was first issued.

2.3  Device ID reuse pattern
     The bot caches device_id in ~/.evilquest/device.json and reuses it
     across every session. A real player's device ID would only exist in one
     browser's localStorage. Seeing the same device_id log in from multiple
     IPs or at inhuman hours (3 AM, continuous) is a strong signal.

2.4  Signing key fingerprint
     The bot registers the same ECDSA signing key for every session. The
     server already stores this key. Flagging accounts where the signing key
     was registered via the API (rather than generated in-browser by the JS
     client) is possible if the browser generates the key differently (e.g.,
     using WebCrypto with specific key usage flags the bot doesn't replicate
     exactly).


==========================================================================
3. WEBSOCKET PROTOCOL DETECTION
==========================================================================

3.1  Packet timing regularity
     The bot's heartbeat is jittered (5.0–6.2 s) but is still generated by
     random.uniform() which produces a uniform distribution. Real human
     heartbeat timing follows a much messier distribution correlated with
     user activity. Statistical analysis of inter-packet intervals over a
     session would distinguish bot from human.

3.2  CLIENT_ACTIVITY only with heartbeat
     The bot always sends CLIENT_ACTIVITY paired with the heartbeat. A real
     player sends CLIENT_ACTIVITY in response to keyboard/mouse events that
     are independent of the heartbeat timer. The server could flag sessions
     where CLIENT_ACTIVITY is perfectly correlated with the ping interval.

3.3  No cursor / mouse movement packets
     If the game tracks mouse position or sends cursor-move events, the bot
     never sends them. Sessions with zero cursor events but active game
     actions are suspicious. The server could require periodic
     CURSOR_POSITION packets and flag accounts that never send them.

3.4  Reaction time is too fast and too consistent
     The bot retargets a new cow within ~500 ms of receiving ENTITY_DEATH.
     Human reaction times vary (200 ms–2000 ms) and follow a log-normal
     distribution. The bot's reaction time will cluster at a fixed offset
     from ENTITY_DEATH equal to the asyncio event loop cycle time. The
     server could measure the delta between ENTITY_DEATH and the next
     PLAYER_INTERACT and flag clients with suspiciously consistent deltas.

3.5  Zero idle time
     Real players pause, read chat, look at their inventory, or go AFK. The
     bot runs a continuous loop with no idle gaps. A session with zero
     periods of inactivity lasting more than 5 minutes over many hours is
     statistically abnormal.


==========================================================================
4. MOVEMENT AND PATHFINDING DETECTION
==========================================================================

4.1  Perfectly optimal A* paths
     The bot always sends the mathematically shortest path. Humans take
     shortcuts, bump into obstacles, and sometimes go slightly the wrong
     way. The server could compare sent paths against the known optimal path
     and flag clients that are optimal 100% of the time over many moves.

4.2  Grid-aligned waypoints only
     Every PLAYER_MOVE waypoint the bot sends is an exact tile centre
     (x*10+5, z*10+5). Real clients, depending on how the JS client
     generates paths, may send slightly off-centre coordinates. The server
     could reject or flag paths where every single waypoint is exactly
     tile-centre aligned across an entire session.

4.3  Path length always at the 50-waypoint cap
     The bot fills PLAYER_MOVE packets to the 50-waypoint maximum whenever
     the path is long. Human players may send shorter paths more often
     (clicking a nearby target). Sessions that always send exactly 50
     waypoints for long moves but vary appropriately for short moves could
     be fingerprinted.

4.4  Systematic cliff probing
     Before the height pre-computation was added, the bot learned the cliff
     tile by tile via PATH_TRUNCATED. Even now, the bot will sometimes probe
     unknown tiles near the cliff edge. A server-side heatmap of
     PATH_TRUNCATED events per account would reveal bot accounts that
     methodically probe the same boundary in a pattern no human would follow.

4.5  No path abandonment
     Humans sometimes send a move command and then click somewhere else
     before arriving, causing the client to send a new PLAYER_MOVE mid-
     journey. The bot always completes or waits for a full path. Sessions
     with zero mid-path redirects are unusual for active players.


==========================================================================
5. COMBAT BEHAVIOUR DETECTION
==========================================================================

5.1  Always targets by type_id, never by name or visual proximity
     The bot uses NPC type_id == 10 to identify cows. It will never
     accidentally click the wrong NPC, never switch targets mid-fight, and
     never get distracted by a different entity. Real players make targeting
     mistakes. Accounts with a 0% mis-target rate over thousands of kills
     are suspicious.

5.2  No food consumption
     If the player character has food items, a real player would eat when
     HP drops low. The bot never eats. If the server tracks HP thresholds
     vs. EAT_ITEM events, an account that never eats food despite regularly
     reaching low HP is a strong signal.

5.3  Instant attack on arrival
     The bot sends PLAYER_INTERACT_OBJECT within one event loop tick of the
     movement completing. A human player clicks the target, waits for the
     walk animation, and then the attack starts — with a small but variable
     delay. A server-side check on the delta between PLAYER_MOVE completion
     and the first PLAYER_INTERACT would catch this.

5.4  Perfect respawn recovery
     After death the bot immediately walks back to the exact same cow spawn
     coordinates. Humans may log out, take a break, or wander. An account
     that respawns and is back fighting within a fixed time window (minus
     walk time) every single death is anomalous.


==========================================================================
6. ASSET AND MAP DATA EXPLOITATION
==========================================================================

6.1  Bot extracted terrain height data from game assets
     The bot downloaded height chunk JSON files from the asset server and
     used them to pre-compute cliff tiles. The server could:
       - Serve height data only to authenticated sessions over an encrypted
         channel that requires the actual game to be running (e.g., via
         a signed JWT valid for one session only).
       - Serve height data as part of the encrypted WebSocket stream rather
         than as static files on the asset server.
       - Randomise terrain passability slightly each patch so cached height
         data becomes stale.

6.2  walls.json and tile chunks are openly accessible
     All map data is served as plain JSON files with no authentication. A
     bot can download the full map offline and run pathfinding without ever
     connecting to the game. Gating asset downloads behind session tokens
     would force the bot to be online to load map data, giving the server
     more opportunities to detect it.

6.3  Dynamic blocks.json persists between sessions
     The bot builds a persistent local cache of impassable tiles. If the
     server periodically changes which tiles are passable (e.g., seasonal
     updates, dynamic events), the cached block list becomes wrong and the
     bot would navigate incorrectly — a detectable anomaly.


==========================================================================
7. CRYPTO AND PROTOCOL HARDENING
==========================================================================

7.1  Opcode mapping is sent in plaintext-inspectable order
     The OPCODE_MAPPING frame is currently sent once per session. If the
     server rotated the opcode map more frequently (e.g., every 60 seconds
     inside the encrypted stream), a bot that failed to handle re-keying
     would break immediately. The current implementation handles it once but
     does not re-key.

7.2  Proof-of-work / JavaScript challenge
     The server could require the client to solve a small proof-of-work
     challenge that is easy in a real browser (Web Workers, WebAssembly) but
     difficult to replicate in Python without significant effort. The
     challenge could be tied to browser-specific APIs (e.g., WebCrypto key
     derivation using a browser-internal entropy source).

7.3  Signed game client attestation
     Require the JS client to sign the session transcript with a key that is
     only accessible inside a real browser context (e.g., stored in
     IndexedDB, generated via SubtleCrypto with non-exportable flag). A bot
     running outside the browser cannot access non-exportable browser keys.

7.4  Canvas / WebGL fingerprinting before login
     Add a canvas drawing challenge on the login page. The server receives
     the canvas hash and cross-references it with the claimed browser. Python
     cannot produce an identical canvas render to Chrome without embedding a
     full rendering engine.


==========================================================================
8. SERVER-SIDE BEHAVIOURAL ANALYSIS
==========================================================================

8.1  Session-level ML anomaly detection
     Train a model on genuine player sessions (movement patterns, timing
     distributions, action sequences) and score each new session against it.
     Flag sessions with anomaly scores above a threshold for manual review
     or automatic soft-ban. The current bot's behaviour would score very
     highly anomalous due to perfect timing, no idle periods, and no
     targeting mistakes.

8.2  Kill rate / XP rate outlier detection
     Track kills per hour per account. The bot can achieve a consistent kill
     rate that no human can sustain for 8+ hours. Flag accounts with a
     standard deviation of kill rate near zero over long sessions.

8.3  Play-hour distribution
     Real players have sleep cycles. A bot running 24/7 has a flat hourly
     activity distribution. Accounts with activity at 3–5 AM local time
     (inferred from IP geolocation) as frequently as prime hours are
     suspicious.

8.4  Geographic impossibility
     If the same account logs in from two different countries within a time
     window that makes travel impossible, flag it. The bot's device_id is
     cached and could be used from any IP.

8.5  Identical pathing fingerprint across sessions
     The bot takes effectively the same route to the cow area every session
     (A* from spawn to cow centre). Recording path sequences and comparing
     them across sessions for the same account would reveal a bot that never
     varies its route.

9. QUICK WINS (LOWEST EFFORT, HIGHEST IMPACT)
==========================================================================

Priority  Measure                              Breaks current bot?
--------  -----------------------------------  -----------------------
HIGH      JA3/JA4 TLS fingerprint blocking     Yes — immediately
HIGH      Require HTTP/2 from Chrome UA         Yes — immediately
HIGH      Server-side kill-rate outlier alert   Soft detection
HIGH      Gate asset JSONs behind session auth  Breaks offline map load
MEDIUM    Rotate opcode map every 60 s          Breaks re-key handling
MEDIUM    Require CURSOR_POSITION packets       Breaks silently
MEDIUM    Canvas fingerprint at login           Yes, hard to spoof
LOW       ML behavioural scoring                Detects over time
LOW       Dynamic map passability changes       Breaks cached blocks


==========================================================================
10. WHAT THE BOT DOES WELL (HARDEST TO DETECT)
==========================================================================

The following behaviours are already implemented and would survive many
of the above countermeasures:

- Chrome-like HTTP headers on login (passes naive header inspection)
- Jittered heartbeat (passes simple timing regularity checks)
- Persistent device ID and signing key (passes device continuity checks)
- Credential storage outside the repo (passes repo scanning)
- Dynamic block learning via PATH_TRUNCATED (adapts to map changes)
- Euclidean wait-time calculation (movement timing is realistic)

The single highest-value fix EvilQuest could deploy today with no client
changes is JA3/JA4 TLS fingerprint enforcement via a reverse proxy
(e.g., Cloudflare, nginx with fingerprint module). This requires zero
game code changes and immediately breaks any Python-based bot.
